# Point-cloud Symmetry Experiments

Small preparatory project for a university laboratory interview, related to a research direction tentatively titled "Symmetry spectra as universal representations of 3D objects".

The project is a deliberately small, controlled learning experiment to answer:

1. How are point clouds represented and processed in PyTorch?
2. How does a PointNet-style architecture build a permutation-invariant global embedding?
3. How do random 3D rotations affect a simple point-cloud classifier?
4. Do learned embeddings separate synthetic shapes with different symmetry structure?

It is a prototype for exploring point-cloud representation, PointNet-style training, rotation augmentation, and embedding analysis — not a symmetry-detector.

## Non-goals and limitations

This project does **not**:

- Solve partial or approximate symmetry detection (cf. Mitra, Guibas & Pauly 2006);
- Use real meshes or ModelNet40;
- Implement PointNet++, transformers, or SE(3)-equivariant networks;
- Use contrastive learning;
- Claim that learned embeddings encode a "universal symmetry spectrum".

> This project does not solve partial approximate symmetry detection. It uses deliberately simplified synthetic labels to explore point-cloud representation, PointNet-style training, rotation augmentation, and embedding analysis. It does not establish that learned embeddings encode a universal symmetry spectrum.

## Data generation and labels

Point clouds are generated with NumPy and returned as `float32` arrays of shape `[N, 3]` (default `N = 256`). Every sample is:

1. Generated by one of five synthetic generators;
2. Centered at the origin (centroid removed);
3. Normalized so the maximum point norm is 1;
4. Optionally rotated with a random 3D rotation matrix (random Gaussian QR);
5. Optionally perturbed with small Gaussian jitter (sigma 0.01).

The binary labels are **controlled synthetic labels**, not detected symmetries:

- `class 1 = rotationally_symmetric`: ring (circle in a random plane), cylinder surface, cube surface.
- `class 0 = asymmetric`: L-shaped union of two boxes, random multi-cluster Gaussian cloud.

`generate_dataset` alternates labels so classes are always balanced and samples several generators per class to avoid single-generator artifacts.

## Model: TinyPointNet

A minimal PointNet-style model (`src/model.py`):

```
input [B, N, 3]
  -> shared point-wise MLP (3 -> 64 -> 128 -> 256, ReLU)
  -> per-point features [B, N, 256]
  -> max pooling over points -> global embedding [B, 256]
  -> classifier (256 -> 128 -> 2)
```

- The same MLP is applied to every point, so the model is permutation-invariant by construction (max pooling is symmetric);
- The 256-d embedding before the classifier is used for the analysis in Phase 6;
- Note: permutation invariance does **not** imply rotation invariance.

Verified in `src/check_pipeline.py`: permuted point order leaves logits unchanged (max |Δ| = 0.0).

## Commands

```bash
# visualize synthetic shapes (canonical vs rotated)
python -m src.visualize

# train an experiment: canonical (A) | rotation_augmented (B) | rotation_shift (C)
python -m src.train --experiment canonical --epochs 20 --seed 42 --device auto
# (or use scripts/run_experiment_a.sh / _b / _c)

# summarize experiment metrics
python -m src.summarize

# embedding analysis: PCA plot + rotation cosine similarity
python -m src.evaluate --experiment canonical --device auto
```

Sanity checks: `python -m src.check_pipeline` (shapes + permutation invariance), `python src/check_data.py` (generators, normalization, balance).

## Experiment results (seed 42, 20 epochs, batch 32)

| Experiment | Train rotated? | Test rotated? | Final test accuracy |
|---|---|---|---|
| canonical (A) | No | No | **1.0000** |
| rotation_augmented (B) | Yes | Yes | **1.0000** |
| rotation_shift (C) | No | Yes | **0.9975** |

Per-epoch curves: `outputs/figures/learning_curve_*.png`. Full metrics: `outputs/metrics/{experiment}.{json,csv}`, `outputs/metrics/summary.csv`.

## Embedding analysis (exploratory)

From a held-out set (400 samples, canonical orientation):

- **PCA** of embeddings (`outputs/figures/embeddings_pca_*.png`): colored by class, marker shape encodes the generator. The same diagnostic must not be described as proof of cluster quality.
- **Rotation cosine similarity** — embeddings of a sample vs its rotated copies:

| Model | Mean cosine (orig vs rotated) | Min cosine |
|---|---|---|
| canonical | 0.9784 | 0.9406 |
| rotation_augmented | 0.9756 | 0.9271 |

Reported only as exploratory diagnostics, not as proof of invariance.

## Interpretation (observation vs conclusion)

- **Observation**: the binary symmetric/asymmetric task reaches ~100% accuracy in all three rotation policies; the rotation-shift model degrades only slightly (0.9975).
- **Observation**: embeddings are highly stable under random rotations (cosine ≈ 0.93–0.98) for both the canonical and rotation-augmented models.
- **Conclusion (careful)**: for this specific binary task, the discriminative point-cloud statistics that TinyPointNet can use are largely rotation-tolerant *even without rotation augmentation*. Consequently, this experiment is too easy to demonstrate a strong rotation-shift effect.
- **What this means for the lab topic**: permutation invariance is guaranteed by the architecture, while rotation robustness is *learned and task-dependent*. On harder tasks (e.g. orientation-sensitive classes, partial symmetry) the difference between Experiments A/B/C would likely be visible; that is a natural next experiment.

## Next steps

- Add a third synthetic class `partially_symmetric` (e.g. repeated legs plus asymmetric top).
- Force a rotation-sensitive task (e.g. distinguishing an object from its 180°-rotated version) to expose the canonical-vs-rotated gap.
- Move to real point clouds (e.g. ModelNet40) with explicit symmetry descriptors.
- Replace the max-pool baseline with stronger geometric models (PointNet++, equivariant layers) only after the baseline is fully understood.
